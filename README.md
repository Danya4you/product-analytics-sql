# Продуктовая аналитика SaaS на чистом SQL

Сквозной кейс продуктового аналитика на PostgreSQL: от сырого лога событий до
решений, которые можно отнести продакту и финансистам.

Данные синтетические — их генерирует скрипт из репозитория. Это сделано
намеренно: в сгенерированных данных заранее известно, какие эффекты в них
заложены, поэтому SQL-запросы можно проверить — они обязаны найти то, что есть,
и не найти того, чего нет. Где выводы ограничены искусственностью данных,
об этом сказано прямо: см. [Границы кейса](docs/findings.md#границы-кейса).

```
регистрации → триал → оплата → жизнь подписки → отток
     ↓          ↓        ↓            ↓            ↓
   каналы   активация  тарифы        MRR      предсказание
```

**11 999** регистраций · **405 000** событий · **20 месяцев** · **9** блоков
анализа · **14** автоматических проверок качества данных

## Четыре результата, ради которых всё это считалось

**Платное привлечение убыточно.** 87,8 % рекламного бюджета уходит на
пользователей, которые не заплатят. Валовая прибыль платных каналов —
минус 13,3 млн ₽; окупаемость контекстной рекламы 22,6 месяца при среднем
сроке жизни подписки 7 месяцев.

**Всё решают первые семь дней.** Активированные (проект + три задачи за
неделю) платят в 4,7 раза чаще: 37,0 % против 7,8 %. Разрыв в удержании
держится до конца наблюдения. Крупнейшая дыра воронки — 3 255 человек
подтвердили почту и не создали ни одного проекта.

**Отток видно за месяц.** Активность ушедших падает на 65,9 % за 28 дней до
отмены, у живых — на 8,7 %. Правило выделяет 13,9 % MRR как зону риска и
превращается в список для поддержки.

**Приглашение коллег ничего не даёт.** Наивно — плюс 11,3 п.п. к конверсии.
Внутри сопоставимых сегментов эффект исчезает целиком (p ≈ 0,9): приглашение
было признаком вовлечённости, а не её причиной.

## Запуск

Нужны PostgreSQL 14+ (проверено на 17.11) и Python 3.8+ **без единой внешней
зависимости**: генератор написан на стандартной библиотеке.

```bash
git clone https://github.com/Danya4you/product-analytics-sql.git
cd product-analytics-sql

export PGUSER=postgres PGPASSWORD=postgres
./scripts/build.sh          # данные, схема, загрузка, витрины, проверки
./scripts/run_analysis.sh   # все девять блоков анализа
```

Windows, PowerShell:

```powershell
$env:PGUSER='postgres'; $env:PGPASSWORD='postgres'
.\scripts\build.ps1
.\scripts\run_analysis.ps1
```

Без локального PostgreSQL — через Docker:

```bash
docker compose up -d
PGHOST=localhost PGPORT=5433 PGUSER=postgres PGPASSWORD=postgres ./scripts/build.sh
```

Сборка занимает около двух минут: 12 секунд генерация, полминуты загрузка
400 тысяч событий, остальное — витрины. Быстрый прогон:
`USERS=4000 ./scripts/build.sh`.

Дашборд пересобирается из базы одной командой — числа в нём не правятся руками:

```bash
python scripts/build_dashboard.py    # → report/dashboard.html
```

Готовый вывод всех запросов лежит в
[report/analysis_output.txt](report/analysis_output.txt), дашборд — в
[report/dashboard.html](report/dashboard.html). И то и другое можно прочитать,
ничего не запуская.

```
sql/
  00_schema.sql          сырой слой app: 9 таблиц, ключи, CHECK-ограничения
  01_load.sql            загрузка CSV через \copy
  marts/                 витрины: dim_user, fct_subscription, fct_mrr_movement, …
  analysis/              девять аналитических блоков
tests/
  data_quality.sql       14 проверок, падают с ненулевым кодом возврата

  generate_data.py       генератор данных, без зависимостей
docs/
  data-model.md          модель данных и три места, где легко ошибиться
  metrics.md             словарь метрик: формула, место в коде, оговорка
  findings.md            выводы с числами и рекомендациями
report/
  dashboard.html         дашборд на чистом HTML и SVG, без библиотек
  analysis_output.txt    полный вывод всех запросов
```

Два слоя: `app` — данные как их отдала бы продакшн-база, `marts` — витрины, на
которые смотрит аналитик. Аналитические запросы обращаются только к `marts`;
каждое обращение к `app` из отчёта — повод спросить, почему нужного поля нет в
витрине. Подробнее — [docs/data-model.md](docs/data-model.md).

## Что в этом кейсе неочевидного

Разбор этих мест — половина ценности репозитория; каждое подробно
прокомментировано прямо в коде.

**Движения MRR считаются из лога событий, а не из разницы месячных срезов.**
Подписка, пришедшая и ушедшая внутри одного календарного месяца, при сравнении
срезов исчезает бесследно: в обоих месяцах у неё ноль. Сходимость двух способов
проверяется отдельным тестом.

**Недели удержания отсчитываются от дня регистрации, а не по календарю.** При
нарезке по ISO-неделям нулевая неделя у зарегистрировавшегося в четверг длится
четыре дня — в когортной таблице это выглядит как провал, которого нет.

**Незрелые когорты отсекаются явно.** Когорта, зарегистрировавшаяся три недели
назад, не может показать удержание восьмой недели. Без фильтра среднее по
столбцу поедет вниз, и это прочитают как ухудшение продукта.

**Отток считается на месяцы под риском, а не на число подписок.** Иначе сегмент
из свежих подписок всегда выглядит стабильнее — просто потому, что уйти ещё не
успел.

**Значимость и мощность разведены.** В разборе A/B считается MDE, и один из
результатов оказывается значимым при эффекте ниже порога чувствительности —
случай, который обычно принимают за победу.

**Корреляция проверяется на отбор.** Раздел 9 показывает эффект в 11,3 п.п.,
который целиком исчезает при сравнении сопоставимых сегментов.

**Статистика считается в самой базе.** В PostgreSQL 17 нет `erf()` — он
появился только в 18-й версии, — поэтому нормальное распределение вычисляется
приближением Зелена — Северо: `marts.norm_cdf()`, `marts.z_two_proportions()`,
`marts.ci95_diff_proportions()`.

## Проверки качества

`tests/data_quality.sql` — 14 проверок, которые база выполнить за себя не может:
согласованность таблиц между собой, соответствие дате среза и сходимость витрин
с сырым слоем. Последнее важнее всего: витрина, молча разошедшаяся с
источником, — худший вид ошибки, потому что отчёт по ней выглядит правдоподобно.

Ключевая проверка — накопленный водопад MRR обязан совпасть с независимо
посчитанным помесячным срезом с точностью до копейки.

Проверки гоняются в CI на каждый push: GitHub Actions поднимает PostgreSQL,
собирает витрины и прогоняет все девять аналитических блоков. Сломанный запрос
роняет сборку.
