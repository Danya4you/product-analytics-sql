# Планы запросов и производительность

Три замера на реальных данных репозитория: 458 628 строк в `marts.stg_events`,
12 039 аккаунтов, PostgreSQL 17.11, ноутбук. Воспроизводятся командой

```bash
psql -d timeline_analytics -f scripts/explain.sql > report/explain.txt
```

Полный вывод с планами — [report/explain.txt](../report/explain.txt).
Абсолютные миллисекунды зависят от машины и состояния кеша; смысл имеет
**отношение между вариантами**.

---

## 1. `STABLE`-функция в списке выборки: ×10 600

Самая дорогая ошибка в этом проекте — на ней сборка витрин однажды перестала
завершаться вовсе.

Функция даты среза сначала выглядела так:

```sql
CREATE FUNCTION marts.snapshot_ts() RETURNS timestamp
LANGUAGE sql STABLE AS $$
    SELECT date_trunc('day', max(occurred_at)) + interval '1 day' FROM app.events
$$;
```

Выглядит безобидно и читается отлично. Проблема в том, что `STABLE` гарантирует
неизменность результата **в пределах одного запроса**, но не обещает, что
PostgreSQL вычислит функцию один раз. В списке выборки она вызывается **на
каждой строке**, и каждый вызов — полный проход по таблице событий.

| Вариант | 200 пользователей | В пересчёте на 12 039 |
|---|---:|---:|
| `max()` внутри функции | **15 102 мс** | ~15 минут |
| чтение `marts.meta` (одна строка) | **1,4 мс** | ~0,1 с |

Разница в **10 600 раз**. Именно поэтому в репозитории функция читает
материализованную витрину из одной строки:

```sql
CREATE MATERIALIZED VIEW marts.meta AS
SELECT date_trunc('day', max(occurred_at)) + interval '1 day' AS snapshot_ts
FROM app.events;

CREATE FUNCTION marts.snapshot_ts() RETURNS timestamp
LANGUAGE sql STABLE AS $$ SELECT snapshot_ts FROM marts.meta $$;
```

Функция по-прежнему вызывается на каждой строке — но теперь каждый вызов стоит
чтения одной страницы вместо сканирования почти полумиллиона строк.

**Как заметить у себя.** В плане появляется узел, чьё `loops=` равно числу
строк результата. Если внутри этого узла что-то читает большую таблицу —
дальше можно не смотреть.

**Альтернатива, если витрину заводить не хочется:** обернуть вызов в скалярный
подзапрос `(SELECT marts.snapshot_ts())`. Планировщик вынесет его в InitPlan и
вычислит однократно. Вариант рабочий, но требует дисциплины во всех запросах
сразу, а витрина чинит проблему в одном месте.

## 2. Коррелированный подзапрос против свёртки: ×5,6

Задача из раздела 9.3: медиана числа событий каждого типа на аккаунт.

Напрашивающийся вариант — на каждой строке лога спросить «а сколько таких
событий у этого пользователя»:

```sql
FROM marts.stg_events e
JOIN LATERAL (
    SELECT count(*) FROM marts.stg_events x
    WHERE x.user_id = e.user_id AND x.event_name = e.event_name ...
) per_user ON true
```

Вариант из репозитория сначала сворачивает лог до «пользователь × событие», и
только потом берёт медиану.

| Вариант | Окно 30 дней |
|---|---:|
| подзапрос на каждой строке | **417 мс** |
| предварительная свёртка | **75 мс** |

На тридцатидневном окне разрыв скромный — подзапрос попадает в индекс, и
PostgreSQL кеширует повторяющиеся вызовы. Но растёт он нелинейно: объём работы
у первого варианта пропорционален числу строк, умноженному на стоимость
поиска, у второго — одному проходу. На девяностодневном окне из настоящего
отчёта первый вариант уже неприемлем, и замер сделан на суженном окне именно
поэтому.

## 3. Индекс — не ускорение, а выбор планировщика

Замер, который не подтвердил ожидание, и поэтому интереснее двух предыдущих.

На `marts.stg_events` есть индекс по `(user_id, occurred_at)`. Проверка,
работает ли он:

| Запрос | План | Время |
|---|---|---:|
| 3a. События одного пользователя | Index Scan, 4 строки | **0,079 мс** |
| 3b. Первая неделя всех пользователей | Seq Scan + Hash Join | **384 мс** |
| 3c. То же с `enable_indexscan = off` | Seq Scan + Hash Join | **409 мс** |

Строки 3b и 3c — **один и тот же план**. Принудительный запрет индексного
доступа ничего не изменил, потому что планировщик и так его не использовал.

Это правильное поведение, а не упущение. Запрос из `dim_user` соединяет **всех**
пользователей со **всеми** их событиями первой недели: нужна практически вся
таблица. Прочитать её один раз подряд и построить хеш дешевле, чем сделать
12 039 отдельных обращений по индексу — при обходе индекса страницы читаются
вразнобой, и выигрыш от точечного доступа съедается случайным чтением.

**Вывод для практики.** Индекс на `(user_id, occurred_at)` в этом проекте нужен
не для построения витрин, а для точечных запросов вроде «покажи активность
конкретного аккаунта» — тех самых, что делает поддержка по списку из раздела
5.4. Для витрин он не работает и работать не должен.

Отсюда же общее правило: индекс, добавленный «на всякий случай», не
бесплатен — он занимает место и замедляет вставку. Прежде чем заводить индекс,
стоит посмотреть в план и убедиться, что запрос действительно выбирает малую
долю таблицы.

## Что не оптимизировалось и почему

Полная сборка занимает около четырёх минут на 12 000 аккаунтов, из них
примерно половина — загрузка CSV на 472 тысячи строк. На таком объёме
дальнейшая оптимизация не окупается: витрины материализованы, повторные обращения к ним мгновенны, а
аналитические запросы укладываются в сотни миллисекунд.

Что стало бы узким местом при росте на порядок:

- `marts.fct_subscription_month` строится боковым соединением с подзапросом на
  каждый месяц жизни подписки. На 17 тысячах строк это незаметно, на миллионах
  потребовало бы оконной функции вместо `LATERAL`.
- `marts.stg_events` пересобирается целиком при каждом запуске, и вместе с ним
  склейка устройств с аккаунтами. Для ежедневной загрузки понадобилась бы
  инкрементальная сборка по `ingested_at` — колонка для этого уже есть.
- `marts.stg_identity` считает владельца устройства оконной функцией по всей
  таблице событий. На миллионах устройств это отдельная задача: связи между
  устройствами и аккаунтами обычно хранят инкрементально, а не пересчитывают.
- Дедупликация через `DISTINCT ON` требует сортировки всей таблицы. На больших
  объёмах дешевле дедуплицировать на загрузке, а не на чтении.
